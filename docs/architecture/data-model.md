# 事件-实体索引

SAG 的全部机制都建立在一个很小的数据结构上。理解它，比记住任何架构图都重要。

> **event 保留语义，entity 负责索引，超边只是它们之间潜在的关系行。**

<EventEntityDiagram />

## 四张表

官方引擎把索引落成关系表（名称按论文与官方 wiki 的描述，`zleap-sag` 内部实现可能略有差异）：

```sql
chunks          (id, source, heading, content, embedding)
events          (id, chunk_id, summary, embedding)
entities        (id, name, type, embedding)
event_entities  (event_id, entity_id)          -- 潜在超边就在这里
```

| 表 | 存什么 | 谁读它 |
| --- | --- | --- |
| `chunks` | **原始文本**，唯一证据边界 | 生成、引用、人工核验 |
| `events` | 每个 chunk 一个自足事件摘要 | 结构路径召回、重排 |
| `entities` | 从原文抽取的索引点 | 种子召回、JOIN 连接键 |
| `event_entities` | 事件与实体的多对多关联 | 查询时动态超边 |

注意 `event_entities` 里**没有任何「图对象」**。它只是行。只有当某次查询执行 JOIN 时，若干行才被临时解释成一条连接多个实体的超边。

## 为什么不拆三元组

| 维度 | 三元组（GraphRAG 常见路线） | 事件超边（SAG） |
| --- | --- | --- |
| 结构 | `主体 → 谓词 → 客体` | `event → {entity₁ … entityₙ}` |
| 语义完整性 | 一段完整语义被切成多条边 | 一个事件自足、可独立理解 |
| 抽取稳定性 | 强依赖谓词抽得准；「使用 / 基于 / 提出 / 支持」易漂移 | 只需总结事件 + 抽实体，任务更稳定 |
| 与原文的关系 | 需要实体合并、关系归一、社区摘要 | 直接映射回原 chunk |
| 增量 | 新关系可能触发图更新与摘要重算 | 追加若干行即可 |

官方作者在公开解读里给出过一组同配置对比：在 MuSiQue 上，三元组式 `1-n-2` 结构 Recall@5 为 **77.16%**，而一事项多实体超边结构为 **80.04%**（BGE-Large-EN-v1.5 + Qwen3.6-Flash，作者公开解读口径）。结论不是「更复杂更好」，恰恰相反：**结构更轻，效果反而更好**。

::: info 实体类别
官方抽取提示词把实体划成若干语义类别（论文与实现中约为 11 类，用于约束「应提尽提」的抽取范围）。具体类别清单会随版本调整，请以[仓库 main 分支](https://github.com/Zleap-AI/SAG)的提示词为准，不要照抄二手文章的分类表。
:::

## 「应提尽提」是什么意思

entity 在 SAG 里**首先是索引点，不是语义本身**。因此抽取策略偏向召回：人名、组织、产品、时间、地点、编号、概念、指标……凡是能帮助另一个 chunk 与它连上的词，都值得抽。真正的语义由 event 承载。

这带来一个反直觉的鲁棒性结论：即便实体抽取不完美、别名没合并干净，系统仍能工作。官方实现明确**不做复杂的 entity resolution**：实体入库前做简单字符串归一，再在同一个 source 内按「同类型 + 同名字」用 SQL 查重复用；不存在就插入。仅靠这层朴素处理，超边结构就已经能跑出论文的效果。

## 潜在超边

形式化地说，一条超边是：

```text
h = ( event_e , { entity_1, entity_2, … , entity_n } )
```

它与普通图的边有两点不同：

1. **n 元**：一端是一个事件，另一端是一组实体，保留 n 元关系，不必拆成两两相连。
2. **潜在**：离线阶段只存 `event_entities` 行；全局超图从未被构建。查询时按本次种子与跳数，把相关的行 JOIN 出来，得到一条或若干条局部超边，用完即弃。

这也是为什么 SAG 常被称为「第三类架构」而不是 GraphRAG 的优化版：**它改变了结构存在的位置与时机**。

## 为什么天然支持增量

| 性质 | 原因 |
| --- | --- |
| 纯追加 | 新 chunk 只新增自己的 chunk / event / entity / 关联行，不修改已有结构 |
| 无全局重算 | 没有社区发现、没有全局摘要、没有 PageRank |
| 并发友好 | chunk 是独立单元；event 抽取、entity 向量化都能批量并发 |
| 可回滚 | 删一个来源只需删它自己的行，不需要重建图 |

对比 GraphRAG：真实世界的数据每天都在变，新实体、新别名、新关系不断出现，旧摘要可能过时——**维护一张大图往往比建一张大图更难**。SAG 把这个问题降级成了数据库的增量写入。

## 常见误用

::: warning 四个不要
1. 把 event 当成「更长的三元组」，继续拆谓词与客体。
2. 为了「图谱更干净」引入重型实体合并 / entity resolution——收益有限，却把增量写入变回全局更新。
3. 把 entity 的类别、别名当成业务主数据来治理；它只是索引点。
4. 在离线阶段把 `event_entities` 物化成一张全局超图对象，等于把成本又搬回写入侧。
:::
