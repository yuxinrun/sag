# 查询时动态超边

「动态」是相对于谁？相对于 GraphRAG 在**写入侧**就把图建好、并在数据变化时重算。SAG 的图从来不存在——直到一条查询抵达，才用 SQL 把相关的局部结构临时连出来。

> **结构以关系行的形式潜在存在；查询时实例化，用完即弃。**

## 一、双路召回种子

查询同时走语义与词法两路：

| 路径 | 召回对象 | 擅长 |
| --- | --- | --- |
| 语义 | chunk / event / entity 的向量表示 | 问句、概念、改写、同义表达 |
| 词法 | 全文 / BM25 | 专名、编号、函数名、标准号、缩写 |

两路共同给出**种子实体**与**种子事件**。只保留一路会在跨文档问题里漏掉链条的起点。官方 wiki 的检索建议也一致：问句和概念用语义，代码标识与精确专名用 `grep` 类词法工具。

官方高精度模式的架构是在 SQL 关系扩展、向量召回与全文检索之后，再引入 LLM 精排；快速模式去掉精排，但**仍然保留多跳检索**——两者都用同一套 event/entity 索引，都不是传统 RAG。

## 二、核心动作：一次自连接

```sql
SELECT DISTINCT ee2.event_id, ee1.entity_id AS shared_entity
FROM event_entities ee1
JOIN event_entities ee2
  ON ee2.entity_id = ee1.entity_id
 AND ee2.event_id != ee1.event_id
WHERE ee1.event_id IN (:seed_event_ids)
LIMIT :frontier_cap;
```

三步语义：

1. 取种子事件关联的 **entity ids**；
2. 查这些实体还连接了哪些**其他事件**（`ee2.event_id != ee1.event_id`）；
3. 排除已经出现过的事件，得到下一跳候选。

`shared_entity` 就是两个事件之间的桥。把它重复 H 次就是 H 跳；每跳都带 `LIMIT`。本站 [最小内核](https://github.com/yuxinrun/sag/blob/main/examples/python/sag_minimal.py) 打印的就是这条语句的逐跳执行结果。

::: tip 为什么这比全局 PageRank 轻
PageRank 类方法需要在（近似）全图上做迭代与排序，数据增量增长时重算成本高。SAG 的扩展范围由**种子 + 跳数 + frontier 预算**共同限定，只碰与本次查询相关的行。代价是：种子选错，后面全错——所以双路召回不是锦上添花。
:::

## 三、局部超边实例化

JOIN 得到的候选事件，连同它们关联的实体集合，被临时解释成一组局部超边：

```text
h₁ = ( ev1 , { A 公司, B 公司, 2024-03, 收购 } )
h₂ = ( ev2 , { B 公司, 张某, C 项目, 2024-06 } )
h₃ = ( ev3 , { C 项目, Atlas 网关, 2025, 可观测性 } )
```

`B 公司` 同时出现在 h₁ 与 h₂，`C 项目` 同时出现在 h₂ 与 h₃——跨文档的证据链就这样被连起来。**注意这里没有创建任何图对象**，只是把查询结果按「事件 + 实体集合」组织了一下。

## 四、预算：SAG 最主要的生产风险

共享实体往往是高频词（公司名、年份、通用概念），一跳就可能带出成百上千候选。防线按这个顺序叠：

| 层 | 手段 | 说明 |
| --- | --- | --- |
| 种子 | `seed_k` | 限制起始事件数 |
| 单跳 | `LIMIT :frontier_cap` | 每跳候选硬上限 |
| 全链 | `max_hops` | 跳数上限，官方高精度模式常见 H=2 |
| 融合 | `top_k`（官方范围 1–50） | 最终返回 chunk 数；不应作为修复低质量查询的第一手段 |
| 请求 | 超时 + 熔断 | 重排阶段尤其需要 |

触顶不是错误，是**正常结果**，但必须同时写 `truncated=True`、保留高相关部分、在答案里声明「基于部分数据」。

## 五、噪声从哪来，怎么处理

本站示例故意埋了一篇年会新闻：它原文含查询词、又与种子事件共享「A 公司」，于是**同时被直召路径和 SQL JOIN 带出来**。这不是 bug，是关系扩展的固有性质。

处理手段按成本从低到高：

1. **跳数衰减**：越晚到达的事件权重越低。
2. **实体区分度**：高频共享实体（公司名）降权，稀有实体升权。
3. **RRF / 双路融合**：结构候选与直召 chunk 用倒数排序融合，避免单路分数不可比。
4. **LLM 精排**：官方 `multi` 策略在融合后引入一次 LLM 重排；`multi_jev` 可交给独立 JEV 服务。
5. **明确拒答**：证据不足时说「现有证据不足以回答」，而不是流畅地编。

## 六、消融告诉了我们什么

以下数字来自官方作者公开解读与英文社区对论文的转述，**口径不同，请勿与 wiki 主表混用**；精确数值请核对 [arXiv:2606.15971](https://arxiv.org/abs/2606.15971) 原文。

| 观察 | 数值（转述口径） | 说明 |
| --- | --- | --- |
| 换成更强 embedding NV-Embed-v2 | MuSiQue R@5 从 80.04% → 81.71% | 只涨约 1.7pp，说明增益主要来自结构而非 embedding |
| 三元组式 1-n-2 结构 | MuSiQue R@5 77.16% | 低于超边结构 80.04% |
| 取消多跳（H=0） | 明显下降（社区转述约 69%） | 关系扩展确实是主要贡献 |
| 去掉结构路径 | 下降更明显（社区转述约 56%） | 双路缺一不可 |
| 轻量 reranker 替代 LLM 精排 | 明显下降（社区转述约 62%） | 精排不是可省的一步 |

另一条值得注意的对照：HippoRAG 2 在原论文里使用更大的 NV-Embed-v2，MuSiQue R@5 约 74%；官方作者因此特别说明，同配置对比（都用 BGE-Large-EN-v1.5）会低估 HippoRAG 2。这类**配置公平性**问题在 [争议与边界](/critical/debate) 里还会展开。

## 七、与 PageRank 类方法的对照

| 维度 | HippoRAG 2 等 | SAG |
| --- | --- | --- |
| 结构时机 | 离线建图 + 在线图排序 | 离线只存关系行，在线 JOIN |
| 多跳机制 | Personalized PageRank 全局传播 | 沿共享实体逐跳局部扩展 |
| 增量 | 新数据可能影响图与排序 | 追加行，不重算 |
| 失败模式 | 种子偏差被图传播放大 | 种子偏差导致链断，但影响范围受预算限制 |
| 规模化瓶颈 | 图规模与全图迭代 | 高频实体的扇出与 JOIN 成本 |
