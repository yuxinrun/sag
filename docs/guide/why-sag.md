# 为什么需要 SAG

如果你已经上线过 RAG 系统，你大概率踩过这个坑：**答案分散在几个文档里，单独看每一段都不太像问题，连起来才是答案**。加 reranker、加大 top_k、换 embedding 都只能缓解，因为丢失的不是相似度，是**关系**。

SAG 的动机不是「再做一个更强的检索器」，而是回应一个更底层的问题：在 Agent 时代，计算应该发生在哪里。

## 一、Agentic RAG 的三个叠加成本

官方作者的公开解读把问题说得很直接：复杂任务里一次检索往往不够，于是让模型多检索几轮——拆问题、循环检索、阅读、再决定下一步。听起来合理，但每一步都可能搜不准：

| 成本 | 怎么来的 |
| --- | --- |
| Token 越用越多 | 每轮都要把候选、推理过程与中间结论重新带进上下文 |
| 延迟越来越高 | 多轮串行检索 + 多次 LLM 判断 |
| 不确定性叠加 | 第一次查错，后续推理建立在错误材料上；查得越多，偏得越远 |

对 Agent 来说，检索准确率不只是「体验问题」，而是**整条行动链路的稳定性问题**。因此更准的检索有两层价值：用更少次数找到正确内容；在必须多次查询时，降低每一步的错误叠加概率。

> **「有多少计算，就有多少智能」——但真正关键的是这些计算发生在哪里。** 是每次用户提问时让 Agent 临时查、临时想，还是在数据进入系统时就把该整理的东西整理好？（引自 SAG 作者 Jomy）

## 二、三条既有路线，三种代价

| 路线 | 抓住了什么 | 结构性代价 |
| --- | --- | --- |
| 向量 RAG | 快，适合静态文档、单跳事实 | 只知道「像不像」，不知道「谁和谁发生了什么关系」 |
| GraphRAG | 意识到文本里有实体与结构 | 三元组抽取、实体合并、关系归一、社区发现、社区摘要，每步依赖 LLM 且可能出错；图每天在变，**维护比构建更难** |
| HippoRAG 2 | 证明必须结合结构化记忆与多跳检索 | 依赖全局 Personalized PageRank 类图排序；海量且每日增量增长时，重算很重 |

还有一条常被忽略的线：**增量写入**。Agent 的数据底座必须持续写入、持续更新、可追溯、可回滚，不能每来一批新数据就重算全局图。国内社区的技术解读也把「append-only 的 event-entity 索引」视为 SAG 最实用的工程性质之一。

## 三、SAG 的答案：把结构留在关系表里

```text
写入侧（轻）  chunk → 1 event + N entities，追加即可
查询侧（重）  SQL JOIN 沿共享实体连出与本次问题相关的局部超边
输出侧（稳）  回到原始 chunk，带引用，可人工核验
```

这样做的收益：

- **新鲜度等于写入**：新 chunk 只加自己的行，不触碰已有结构。
- **天然并发**：chunk 是独立单元，event 抽取与向量化都可以批量并发。
- **不做全局实体合并**：官方实现只在同一个 source 内做简单字符串归一与 SQL 查重复用实体；因为 entity 首先是索引点，语义由 event 保留。
- **没有全局排序**：多跳是数据库里的关系扩展，不是一次全图 PageRank。

## 四、决策树

1. **语料以单文档、单跳事实为主？** 是 → 向量 RAG 足够。
2. **需要跨文档、跨段落把事实连起来？** 否 → 保持现状；是 → 继续。
3. **数据持续增量写入，且不能接受离线重建？** 是 → SAG 类架构优先。
4. **核心需求是主题级综述、能接受离线建图？** 是 → GraphRAG 的社区摘要仍有价值。
5. **只需要一个确定数值？** 是 → 直接查业务库或指标 API，别用检索架构解决。

真实系统往往是混合的：SAG 负责结构化多跳，向量与全文负责语义召回，Agent 负责决定何时调用。

## 五、面向 Agent 的两个典型场景

| 场景 | 为什么 SAG 合适 |
| --- | --- |
| 长期使用的数据底座 | Agent 会连续查很多次，第一跳错误会污染整条链路；Recall@2 这类「少结果里早命中」的指标比 Recall@10 更重要 |
| 记忆 | 记忆不是孤立文本，会随时间补充、修正甚至推翻。event 保留完整事项，entities 把人 / 项目 / 偏好连起来，再叠加时间与来源 id 判断当前状态 |

官方作者强调：SAG 能做记忆，不是因为多加了一个 memory 模块，而是因为它本来就在给数据建立「事项、实体、时间、关系」的索引。

## 六、把质疑也读一遍

SAG 不是没有争议。国内技术社区提出过四点很值得进阶读者认真对待：**关系库 vs 图数据库的性能命题、叙事是否被包装、实验配置是否公平、以及超边结构与已有超图 RAG 的关系**。这些不是可以跳过的脚注，见 [争议与边界](/critical/debate)。
