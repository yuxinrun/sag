# 相关工作与四点质疑

一个方法的价值，一半在它做了什么，另一半在它**不适用**于什么。本章汇集国内外公开讨论中的主要观点，其中社区质疑不是官方结论，也不代表本站立场——列出来是为了让你带着判断去采用。

## 相关工作对照

| 路线 | 结构时机 | 多跳机制 | 与 SAG 的关系 |
| --- | --- | --- | --- |
| 向量 RAG | 索引时建向量 | 单次近邻 | SAG 的直召路径仍保留它 |
| Microsoft GraphRAG | 索引时建图 + 社区摘要 | 图 / 社区层级 | 官方论文的主要对照对象 |
| LightRAG | 索引时建实体-关系索引 | 双层并行向量检索 | 同为「轻量结构化」路线，但不做查询时超边 |
| [HippoRAG 2](https://arxiv.org/abs/2502.14802) | 索引时建知识图谱 | Personalized PageRank | 论文主基线；全局图排序 vs 局部 SQL JOIN |
| 超图 / n 元关系 RAG | 多为物化超图 | 超边遍历 | 概念相邻，差别在「潜在 vs 物化」 |
| SAG | 索引时只存关系行 | 查询时 SQL JOIN | 自称区别于 RAG 与 GraphRAG 的第三类架构 |
| SAG2（后续工作） | 去掉 embedding | SQLite FTS5 + BM25 + JEV 重排 | 见 [SAG-Benchmark](https://github.com/Zleap-AI/SAG-Benchmark) |

对比 GraphRAG 框架在生产中的索引开销与多跳经济性，可参考 [llms.blog 的框架对比](https://llms.blog/posts/graph-rag-in-production-comparing-microsoft-graphrag-lightrag-fast-graphrag-and-hipporag-architecture-indexing-overhead-and-multi-hop-retrieval-economics)。

## 国内社区：四类值得认真对待的质疑

以下内容归纳自中文技术社区的公开解读（如微信公众号「老刘说 NLP」的长篇分析、「矩斗安全研究」的论文精读、「PaperAGI」与「暗灯 Lab」的对读文章），**属于社区观点，不是官方结论**：

### 1. 这到底是新方法，还是「图数据库换成关系型数据库」的性能命题？

批评意见认为，SAG 的收益很大程度来自**关系库的成熟工程能力**：MySQL / PostgreSQL 的并发读写、索引、连接池与运维生态远好于多数图数据库；把结构放进关系表，本身就带来规模优势，未必全归功于「超边」这一概念。

**本站看法**：这个质疑成立且重要。它提醒你复现时要控制变量——如果换成图库但保持同样的 JOIN 逻辑与预算，差距还有多大？对工程选型的实际启示是：**先用你团队最熟的关系库，别为了「图」去引一套新存储**。

### 2. 叙事是否被包装了？

有文章认为，event + entities 与已有的「文档-实体倒排」「超图 RAG」「结构化索引」思路存在明显亲缘关系，论文的表述偏重架构叙事。

**本站看法**：概念亲缘确实存在，但「潜在超边、不物化全局图、append-only」这三条组合起来是可检验的工程差异。判断时看实现与消融，不看命名。

### 3. 实验配置是否公平？

公开讨论里最常见的两点：一是基线（HippoRAG 2）原论文使用更大的 NV-Embed-v2，在 BGE-Large-EN-v1.5 下分数偏低；二是不同来源的语料切分、dev 子集、评测脚本不同，导致 Recall@5 出现 80.04 / 80.36 / 88.00 / 93.34 等多个数字。

官方作者其实主动说明了第一点，并给出 SAG 换 NV-Embed-v2 后 MuSiQue R@5 从 80.04% 到 81.71% 的对照，用来论证「增益主要来自结构」。**但主动说明不等于争议消失**：跨来源数字仍不可混用，见 [基准与复现](/paper/benchmarks)。

### 4. 适用边界在哪？

官方 wiki 主表里，SAG 在 **2WikiMultiHopQA 的 Recall@5 上低于 HippoRAG 2**（88.00% vs 90.35%）。也就是说，「全面 SOTA」并不成立。此外，若语料缺少跨文档共享实体，JOIN 扩展带不来新证据，反而多了抽取成本。

**本站看法**：SAG 的强项是「组合式多跳 + 增量写入 + 少结果里早命中」，不是所有多跳场景。选型回到 [为什么需要 SAG](/guide/why-sag) 的决策树。

## 其他国内外解读里有用的补充

| 来源 | 有价值的点 |
| --- | --- |
| 官方公众号「智跃 Zleap」（作者 Jomy） | 一手叙事：Agentic RAG 的三重叠加成本、「计算应该发生在哪里」、chunk 作为并发单元、记忆场景 |
| 「矩斗安全研究」论文精读 | 用「不预建全局图、SQL JOIN 逐跳扩展、动态实例化局部超边」三句话概括机制 |
| 「PaperAGI」 | 把 SAG 理解为「把 GraphRAG 最重的结构化多跳检索交给 SQL」 |
| 「暗灯 Lab」 | 把 SAG 与 GraphRAG 在威胁情报（CTI）场景对读，共同敌人是「捞不全、拼不起」 |
| 网易 / 腾讯新闻转载稿 | 用侨批、《给阿嬷的情书》等例子解释跨文档线索；「5 亿条数据秒级」属媒体转述，无可复现配置，本站不作为事实引用 |
| CSDN 等入门文章 | 常用「收购 B 公司 → CTO → C 项目」三文档例子；索引成本类数字多为民间估计，不可验证 |
| [DEV Community 英文解读](https://dev.to/wonderlab/open-source-project-of-the-day-116-sag-multi-hop-rag-retrieval-via-sql-joins-instead-of-6j7) | 强调「用 SQL JOIN 替代 PageRank」，并整理多跳、结构路径与 reranker 的消融数字 |
| 英文技术站点（Run This AI、ArxivLens 等） | 关注「保留 n 元关系」「append-only 索引」这两点形式化贡献 |

::: warning 关于二手数字
社区文章常把不同来源的数字混在一张表里，或把厂商演示说成基准结果。本站的处理：凡未找到可复现配置与脚本的数字，一律标注为「媒体 / 社区说法」并排除在结论之外。
:::

## 本站的采用建议

| 你的情况 | 建议 |
| --- | --- |
| 语料跨文档、共享实体多、持续增量写入 | 值得评估 SAG；先用官方应用跑一份自己的语料 |
| 单文档问答、数据量小 | 向量 RAG 更省，不必引入抽取成本 |
| 需要主题级综述、可接受离线建图 | GraphRAG 社区摘要仍有价值 |
| 需要确定的结构化数值 | 直接查业务库 / 指标 API |
| 团队没有图数据库运维经验 | 反而是采用 SAG 的理由：关系库成熟、生态完整 |

最后一条纪律：**在自己的语料上做一次 A/B**。论文数字来自英文维基多跳问答数据集，与你的中文业务文档、专有名词分布、噪声比例可能相差很远。
